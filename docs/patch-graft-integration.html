How to read this report

This report assumes you know PATCH well and know nothing about graft.

  • Part I (sections A to E) explains graft itself: what it is, how it builds its index, what a query returns, which of its features PATCH would use, and the words graft uses. Read it first. Every graft term used later is defined in the glossary.

  • To have an AI agent implement it, give it patch-graft-implementation-prompt.md (next to this file). That prompt repeats the graft facts from this report and treats every statement about PATCH's internals as a hypothesis the agent must check in the PATCH repository before it changes code.

Part I: graft for newcomers

A. What graft is

  • A code index for AI coding agents. graft is a command-line tool, written in TypeScript and shipped as an npm package that runs on Node.js. It reads a source repository and builds an index of it, called the map: every file, every function, class, method and type in it (each one a symbol), where each one starts and ends, and which symbol calls, imports or extends which. It then answers questions from that index.
  • The problem it solves. Without an index, an agent looking for code runs a text search, opens a file, follows a call, opens another file, and so on, spending tool calls and context on files it then throws away. With graft, the agent asks one question ("where are retries configured", "who calls init_can_bus") and gets a short ranked list of file:line ranges, with the relevant lines of code included, from which it reads only what it needs. Upstream reports 46 % fewer tool calls and 60 % less time on its own benchmark (README.md:33-40); that is the project's claim and has not been measured on EBS.
  • Local and deterministic. The index is built by parsing each file with tree-sitter, a widely used open-source parsing library with one grammar per language. Building and querying the index uses no AI model, no API key and no network.
  • An AI layer on top. An extra step, graft build --deep, sends the source files to a language model, which writes a one-line summary of every symbol, picks its crux (the up-to-8 lines that matter) and writes concept nodes that explain each system of the repository. Searches then rank better, and results are shorter and easier to read. PATCH requires this layer and builds it through the same LLM endpoint, with the same token, that PATCH itself uses; graft's automatic deep builds, switched on globally with a threshold PATCH sets, keep it current (section 7.1).
  • Four questions it answers. These are the four commands PATCH would use (section 8):
    CommandQuestionComparable to
    graft ask"Where is the code that does X?" Ranked hits for a plain-language or identifier query, with code excerpts.A search engine over symbols, not over raw text.
    graft grep"Every place this text or regex occurs." Complete, not ranked to a top few; hits are grouped by the function they are in.rg, restricted to indexed files, with the enclosing function named.
    graft skeleton"What is defined in this file?" Every definition's signature and line range.An outline view of one file.
    graft callers"Who calls this function?" or "what does it call?", optionally several levels deep ("what breaks if I change it").An IDE's call hierarchy.
  • Languages. C and C++, the main EBS languages, are indexed at graft's "broad" level: functions, types and other symbols, plus call edges matched by name (README.md:525-528). graft does not resolve types the way a compiler does, so expect calls through function pointers or macros to be missing, and calls to same-named functions in different files to be matched to the wrong definition at times. How often this happens on EBS has not been measured. verify Bash, CMake, Make, Perl, Python, XML, YAML, JSON and others are covered too (README.md:474-549). graft languages --json prints the exact list for an installed copy.
  • Where it comes from. graft is an open-source project (MIT licence) by NanoNets, on GitHub as NanoNets/Graft; this report calls it upstream. Upstream has since renamed the product Trail-code, added a second feature called learnings, and added an optional cloud service; the graft command and the @nanonets/graft package still work (README.md:48-49, 125-137). PATCH would use the company's own fork: a copy of upstream that switches off every cloud and telemetry feature for good (docs/no-cloud-policy.md) and is published to the company's Artifactory as @nanonets/graft, version 0.28.0 at the time of writing. Section 3 explains why the package must come from that registry and not from the public npm registry.

B. How graft works

graft build <repo> graft ask | grep | skeleton | callers (minutes on a big repo, then incremental) (each call: load the map, answer, exit) repo files ──► which files? ──► parse each file ──► symbols + edges ──► map folder ──► query ──► JSON on stdout (read only) files git sees, tree-sitter, "foo() at L10-L40 wiring.json loads minus excluded one grammar per calls bar()" ask index the map folders language cards, caches
  1. Choose the files. graft indexes the files git knows about: tracked files plus untracked files that git does not ignore (git ls-files --cached --others --exclude-standard in gitVisibleFiles, src/ingest/fs.ts:331-451), minus folders excluded with --exclude-dir. Languages it has no grammar for are skipped.
  2. Parse. Each file is parsed with its tree-sitter grammar. The grammars are compiled native modules (.node files, in effect DLLs) shipped inside the package; for C and C++ only a Windows x64 build is shipped (section 3).
  3. Extract. From each parsed file graft records its symbols (name, kind, line range, signature) and its edges (calls, references, imports, implements, extends). Edges between files are matched by name.
  4. Write the map. Everything goes into one folder, the map folder: .graph/wiring.json (the wiring graph), an ask index used for ranking, one markdown card per source file, and caches (README.md:461, 470). By default this folder is graft/ inside the repo or a per-user folder elsewhere; PATCH puts it in its own data folder (section 6). The map holds code text, so it is as sensitive as the source (section 11).
  5. Rebuild incrementally. Every parse is cached by a hash of the file's content, so a rebuild only re-parses changed files. On graft's own repo (312 files) a cold build takes about 5 s and a rebuild after one edit about 0.6 s (README.md:466). EBS has not been measured.
  6. Query. Each query command loads the map, answers, and exits. By default graft first checks whether any file changed since the last build and rebuilds if so (a refresh). PATCH switches that off with --no-refresh and rebuilds on its own schedule instead (section 13), because a refresh inside a query makes its time and memory unpredictable.
  7. Large repos. One map has a hard size limit of about 483 million characters of wiring.json (section 7). A repo too big for one map can be built as several parts, each with its own map, plus a small index that lets queries search them all.
  8. The AI layer (build --deep). The same build, plus language-model calls: each new or changed source file is sent whole to the endpoint (about two calls per file: one for the summaries, one for the crux excerpts), then batches of summaries are sent to write the concept nodes (src/context/build.ts:188-512, src/graph/enrich.ts:97-267). Results are cached by content hash, so a later deep build only pays for what changed. A plain build keeps the layer: unchanged symbols keep their summary and crux, changed ones are marked stale and keep the old text until the next deep build (src/graph/enrich.ts:120-145).

An agent would now open exactly those line ranges. saved says that answering this by reading the two files involved would have cost 34,894 characters of context (section 14).

"Where is the map folder of a repo chosen?"

> graft ask "where is the map folder of a repo chosen" . --json --source -n 2 --no-refresh
{
  "query": "where is the map folder of a repo chosen",
  "mode": "lexical",
  "hits": [
    { "kind": "symbol", "title": "own-folder.ts · file", "pointer": "src/skills/own-folder.ts",
      "snippet": "Protects Trail-managed subfolders from symlink redirection …", "score": 1.0136 },
    { "kind": "concept", "title": "Code map directory resolution", "pointer": "src/context/map-dir.ts",
      "snippet": "Decides where the repo's code map lives: …", "score": 1 }
  ],
  "coverage": 0.825, "coverageStrong": 0,
  "saved": { "files": 2, "baselineChars": 5369 },
  "notesChecked": true,
  "notes": [ … two team learnings from .trail/learnings/, with absolute paths and full text … ]
}
  • mode: "lexical" means the query was ranked as words against symbol names, paths and text. A query phrased as "who calls X" or "what imports X" switches to "structural" and walks the graph instead (src/ask/ask.ts, see glossary).
  • The second hit is a concept hit: graft's own repository was built with --deep, which writes those pages. PATCH's maps have them too, once the deep build of section 7.1 has run. Its snippet is model-written text; PATCH marks it as such (section 10).
  • coverageStrong: 0 means none of the query's words matched a name or path of the top hit, which marks this as a weak result (section 8.1).
  • notes are learnings read from files in the repo. They carry absolute paths and free text written by agents. PATCH removes them (section 10).

D. What PATCH uses, and what it leaves out

On a developer's machine, graft is normally installed globally and wired into the developer's AI assistant: graft init writes instruction files and configuration into the repo so the assistant knows to call graft, and from then on graft refreshes itself, reports what it saved and nudges the assistant towards its own commands. PATCH needs none of that wiring. It uses graft only as an index builder and a query engine behind its own tools.

E. Glossary

TermMeaning
map (map folder, context graph)Everything graft build writes for one repo, in one folder: the wiring graph, the ask index, cards and caches. graft's own help text sometimes calls it the "context graph" or the "graft map".
wiring graph, wiring.jsonThe core of the map: one node per file and symbol, one edge per call, reference, import, implementation or inheritance. Stored as one JSON file, .graph/wiring.json, which every query loads into memory.
ask indexA side file of the map with the text graft ask ranks against, including symbol bodies.
cardA small markdown file per source file, listing its symbols with line ranges and signatures. Meant for assistants that read files directly; PATCH does not need them.
concept nodeA markdown page explaining one system of the repository and listing the files it covers, written by a language model during build --deep. ask returns it as a hit of kind concept, whose pointer is a comma-separated list of those files.
summaryA one-line description of a symbol, written by a language model during build --deep. ask ranks against it and shows it as the hit's snippet; skeleton shows it per entry. Stale when the symbol changed since: it is kept, but may describe old code.
symbolA named definition: function, method, class, struct, type, macro, variable and so on.
span, pointerA line range, written L110-L118. A pointer is a repo-relative path with an optional span: src/x.c:L10-L40.
edge, relationA link between two symbols. The relation names its type: calls, references, imports, implements, extends and similar.
in-degreeHow many edges point at a symbol. grep sorts its groups by it, so heavily used functions come first.
crux, excerptThe key lines of a definition (up to 8) that an LLM picked during build --deep, stored as text in the map. ask --source shows the crux instead of the whole definition unless --full is given; then, or for a symbol without a crux, it shows the whole definition read from disk, up to 80 lines (src/ask/ask.ts:1375-1393). A changed symbol keeps its old crux until the next deep build.
lexical / structural modeHow ask handled a query. Lexical: ranked by words against names, paths and text. Structural: the query named a symbol and a relation ("who calls X"), so graft walked the graph from it.
coverage, coverageStrongNumbers from 0 to 1 in an ask result: the share of query words the top hit matched, in any field or only in its name and path. Low values mean a weak answer.

In the fork's current code, a parts build also writes links (.cache/links.json in the root map folder): the calls, imports and references that cross from one part into another, which no part's own map can settle. graft parts lists the parts.
scopeIn a parts build or a folder of several repos, the label of the part a hit came from.
profile storeA folder outside the repo where graft keeps maps, one sub-folder per repo, named after the repo folder plus a hash of its path. Lets graft index a repo without writing into it.
refresh, fingerprintBefore answering, a query compares the files on disk against a fingerprint saved by the last build and rebuilds changed files. --no-refresh skips this and answers from the map as it is.
savings, baselinegraft's estimate of the context it saved: the characters of the files an answer covers (baselineChars) against the size of the answer.
nudgeA hint graft appends to text output, telling an assistant which graft command to use next. Not present in JSON output.
auto-initgraft rewriting the assistant instruction files in a repo after it was updated. Off in PATCH.
learnings, notes, TrailUpstream's second feature: short markdown notes ("decided", "ruled out", "watch out") that agents save in .trail/learnings/ and that ask returns as notes. A repo "on trail" (with .trail/) also keeps its map in .trail/cache/ (section 6). "Trail switch" is graft moving a repo's wiring from graft to the trail command. None of this is used by PATCH.

MCPModel Context Protocol: a standard way for AI assistants to call tools in another process over stdio. graft offers its queries as MCP tools (graft mcp).
tree-sitter, grammar, prebuildtree-sitter is an open-source parsing library. A grammar teaches it one language. graft uses grammars compiled to native Node modules (.node files); a prebuild is such a module compiled in advance for one platform, so nothing is compiled on the target.
upstream, forkUpstream: the public NanoNets project. Fork: the company's copy, with cloud features disabled, published to the company's Artifactory.

Part II: the integration

1. Summary

  • Goal. Give PATCH agents (the main session and Scouts) a fast, exact way to find code in EBS: ranked search, complete text search, file outlines and call hierarchies, answered from an index instead of by grepping and reading whole files. Part I explains the tool that provides this.
  • Recommended approach. PATCH ships a pinned copy of the graft npm package in its signed payload and runs it with PATCH's own Node 24.18.0. A new Prepare step builds the map into PATCH's data folder, then a background job adds the AI layer (build --deep: summaries, crux excerpts, concept nodes) through PATCH's own LLM endpoint and token, and graft's automatic deep builds keep it current. Four typed tools in the guardrails extension (code_search, code_find_all, code_outline, code_callers) run read-only graft queries through a new trusted operation. Before anything reaches the model, PATCH filters the JSON results with its existing guards (credential paths, protected trees, child budgets, the 12,000-character cap).
  • What not to use. PATCH cannot use the way graft normally connects to an assistant (section D). Sessions start with noContextFiles, noExtensions, noSkills and no MCP extension, so the instruction files graft init writes, graft's MCP server and its rule files are never seen by the agent. workspace_shell is the wrong channel too: it runs at Low IL, the repo is read-only there, and user shell commands are blocked.
  • No graft code changes are needed. The graft command line already provides everything required: build, ask/grep/skeleton/callers --json, --no-refresh, and a map folder outside the repo (--dir). PATCH must still pin graft's process environment (section 5) so graft writes nothing into the checkout, does not pick up the developer's own graft settings, and connects to nothing but PATCH's LLM endpoint, and to that only during a deep build (PATCH's own or an automatic one).
  • Facts that change the design.
    • The deep build sends every indexed source file whole to the LLM endpoint. Only --exclude-dir keeps a file out, so everything PATCH's guards hide must be expressible as a folder, path or glob there, and PATCH's approval for its own endpoint must cover EBS source code sent from the background (section 7.1).
    • Automatic deep builds run in a detached process outside PATCH's job queue, with the token they started with and a fixed 3-hour limit, and never use --only-dir (section 7.2).
    • graft's MCP tools return only markdown text, not JSON, so PATCH runs one graft process per query instead of keeping one running (section 9).
    • callers --json does not search across the parts of a multi-part build (section 8.4).
    • One map is capped at about 483 M characters, so a repository of EBS size probably has to be built in parts (--all-parts). Limiting it to some folders with --only-dir does not work with automatic deep builds, which would build the whole repository (section 7).
    • A map or a .trail/ folder that a developer left in the checkout takes precedence over any outside map folder, and graft may even move files inside the checkout. PATCH avoids this by always naming the map folder explicitly with --dir and GRAFT_DIR (section 6).

4. Bundling into the PATCH payload

  1. Fetch on the release builder: npm pack @nanonets/graft@<pinned> --@nanonets:registry=<fork npm URL>, then record the tarball's integrity hash.
  2. Install the production tree with no lifecycle scripts: 
    mkdir engine\graft && cd engine\graft
npm init -y >NUL
npm install --omit=dev --omit=optional --ignore-scripts --no-audit --no-fund ^
    --@nanonets:registry=<fork npm URL> <path>\nanonets-graft-0.28.0.tgz
    Use --ignore-scripts deliberately. graft's postinstall (scripts/postinstall.mjs) does two things, and PATCH wants neither on the builder:
    • it adds @nanonets:registry=… and @trailhq:registry=… to the user's ~/.npmrc;
    • it creates a random install id in ~/.graft/telemetry.json.
    The script itself says the id is minted on first use instead when scripts are skipped. tree-sitter's node-gyp-build install step is not needed either, because the win32-x64 prebuild is loaded at runtime.
  3. Add the tree to the payload: include engine/graft/** in payload-manifest.json (files[], SHA-256), so engine/host/install-integrity.js covers it. Today engine/ is protected only through engine/bin/, engine/host/, engine/contract/, engine/extension-groups.json and engine/package.json (install-integrity.js:10-18), so add engine/graft/ to SAFETY_PATHS.
  4. Add a preflight check next to the rg/fd check (engine/host/preflight.js:82-117, id pi_tools, severity warn). Trusted operation (sketch)

// trusted-tools.js (sketch, not drop-in)
const GRAFT_OPS = new Set(['ask', 'grep', 'skeleton', 'callers']);
export async function graftQuery(repoRoot, op, positional, flags, { stdin } = {}) {
  if (!GRAFT_OPS.has(op)) throw new Error('graft: op not allowed');
  for (const t of positional) assertSafeToken(t);           // no leading '-', no ; CR LF
  const argv = [GRAFT_JS, '--dir', patchMapDir(repoRoot) /* section 6 */,
                op, ...positional, repoRoot, ...flags, '--json', '--no-refresh'];
  const res = await runFixed(NODE_EXE, argv, {
    cwd: repoRoot, env: graftEnv(/* section 5: GRAFT_DIR, GRAFT_NO_REFRESH=1, ... */),
    stdin, timeoutMs: 30_000, maxStdoutBytes: 8 * 1024 * 1024,
  });
  if (res.code !== 0) return { ok: false, diagnostic: firstLine(res.stderr) };  // "✗ no symbol ..."
  return { ok: true, json: JSON.parse(res.stdout) };
}

  4. Mark model-written text: give each hit aiWritten: true when its snippet is a summary or concept prose (and likewise each skeleton entry with a summary), and aiStale: true when the symbol changed since the last deep build. Code from disk (--full) is never marked.
  5. Drop notes, notesChecked and notesHint from ask results. They are learnings read from .trail/learnings/ in the repo: free text written by other agents, with absolute paths (section C), which PATCH has not vetted.

11. Security and policy

  • One outgoing connection. Deep builds, PATCH's own (section 7.1) and graft's automatic ones (section 7.2), send source files to PATCH's own LLM endpoint, and nowhere else. They use the token PATCH itself uses, read fresh from where PATCH keeps it; it lives only in the environment of the deep build or trigger query (and the runner that inherits it), and never reaches argv, a file, a log or the agent. Plain builds and agent queries get no LLM variables at all.
  • No other network. With the section 5 environment and no --lsp or blast --name, graft makes no other outgoing requests:
    • the update check is off (DO_NOT_TRACK);
    • price downloads are off (GRAFT_PRICES_AUTO_UPDATE=0);
    • fetching and look-back are off by default, and stripping TRAIL_* keeps them off;
    • cloud and telemetry are hard-off in the fork;
    • the savings report to Oracle is opt-in and stored in ~/.graft, which is isolated.
    Check this by running the acceptance tests with outbound traffic blocked, except for PATCH's endpoint while a deep build runs.
  • Integrity. The graft tree is part of the signed, hash-pinned payload (section 4). PATCH never runs npx or an install on the target.
  • Integrity level. Builds and queries run as trusted Medium-IL operations, never through Low-IL workspace_shell (that guard sits around index.ts:1999-2021; user shell commands are blocked at :2274).
  • Data in the map. The map stores signatures, spans and the ask index, which includes symbol body text (writeGraph moves body_text into the ask sidecar), plus the AI layer: summaries, crux excerpts and concept nodes written from the source. Treat the store as being as sensitive as the source: put it under the PATCH data folder with the same ACLs, and delete it when the repo is removed.
  • Excluded paths. Files that .piignore or the credential guard hide must not be indexed, and must never be sent to the LLM. Pass them as --exclude-dir entries on every build (the saved list is replaced each time, so a build that forgets one re-admits it), prove it with canary files and a captured request log, and keep the post-filter as a second line of defence.

13. Freshness

The map describes the code as it was at the last build. After an edit or a branch switch it is out of date until the next build, and answers may point at moved or missing lines.

  • Agent queries always use --no-refresh, so a tool call never triggers a rebuild in a process that holds over 1 GB, and never starts an automatic deep build.
  • Rebuild in the background, as a single serialised job per repo, at these points:
    • each Prepare;
    • after source_edit succeeds (debounced);
    • after a branch switch.
    The rebuild is graft build <repo> without GRAFT_NO_REFRESH. It is incremental (extraction cache), and graft's own refresh runs it in a short-lived child (src/graph/refresh-run.ts).
  • Add the graph age to each tool result (for example "graph": {"builtAt": …, "stale": bool}). graft build --check --json reports drift without building.
  • If file times can't be trusted (network drives, restored checkouts), set GRAFT_REFRESH=hash for the build (env-cli.ts:389-403). It is slower.
  • The AI layer goes stale more slowly than the code. A plain rebuild keeps summaries and crux excerpts for unchanged symbols and marks changed ones stale (src/graph/enrich.ts:120-145). PATCH reads graft staleness --json --no-refresh (StalenessReport, src/graph/refresh.ts:645-659: totals.stale, totals.unsummarized, pct) after each rebuild for the ai state it shows. Keeping the layer current is graft's auto-deep, on globally with PATCH's threshold (section 7.2): after each successful plain rebuild PATCH runs its trigger query, which starts a run only when the share reaches that threshold, never on every edit. PATCH queues its own deep build only for the first build or as a retry after a failed run. It ignores graft's recommended flag, the manual nudge.
  • While totals.stale > 0, code_search passes --full, so no old crux is shown under a new line range, and marks stale summaries aiStale (section 10). Add "ai": {"builtAt": …, "stale": n, "unsummarized": n, "state": …} next to the graph age, with "updating" while an automatic run is running and "failed" after a failed one.

14. Savings reporting

graft estimates how much context each answer saved: the size of the files an answer covers (what an agent would otherwise have read) against the size of the answer. This is optional for PATCH, but it is a cheap way to show the value of the feature.

  • ask --source returns saved: {files, baselineChars}. grep, skeleton and callers return a Savings object (src/context/savings.ts:22-27). Sum them per session in PATCH and show them in the status bar, using PATCH's own model and price data.
  • Passing --agent-model is only useful for graft's own ledger, which sits in the isolated home. PATCH can skip it.
  • Do not rely on graft's human savings or nudge lines. They appear only in text output and are disabled on stderr by GRAFT_STDERR_SAVINGS=0.

16. Acceptance tests

  1. Preflight passes on a clean machine. Renaming vendor/c makes it warn, and PATCH still starts.
  2.   3. With outbound traffic blocked and a network capture running, a plain build and 50 mixed queries make no connection attempts, and a deep build (PATCH's own or an automatic one) connects only to PATCH's own endpoint.
  4. For each tool, a known symbol returns spans that match the file on disk, and an unknown symbol returns a diagnostic, not an exception.
  5. A query matching a credential file or a protected tree returns no path or code from it, in the main session and in a Scout.
  6. The output never exceeds 12,000 characters. truncated is set when it would.
  7. After a source_edit, the background rebuild finishes, and the next query sees the new span.
  8. A developer's own graft env settings (for example GRAFT_DIR, TRAIL_NO_FETCH=0) have no effect inside PATCH.
  9. Concurrency: three Scouts querying at once stay within the configured process limit and memory budget.
  10.
